ROOM HOST USE CASE DIAGRAM
Source snapshot: 2026-11-25
One page, one boundary, one primary actor. Six management goals plus three independent workspace goals.
Each management goal groups a mandatory read/view behavior and conditionally selected actions.
Include arrows point from management to the included viewing use case. Extend arrows point from an optional action back to its base management use case.
These are user-goal relationships, not calls to Java methods and not control-flow arrows.
Visual order follows setup and operation: property, inventory, viewing, tenancy, billing; account and monitoring are independent.
No mandatory viewing, contract or utility-before-rent ordering is implied.

H01: PropertyRegistrationController, PropertyRegistrationService, PropertyEditService, HostPropertyController, HostPropertyService.
H02: HostRoomTypeController/Service, HostRoomsController/Service, PublicAccommodationPolicy.
H03: HostViewingController/Service, ViewingService.
H04: HostRoomsController/Service, RoomTenancyService, RentalContractController/Service, RentalContractScanService.
H05: RoomUtilityController/Service, RoomBillingController/Service.
H06/H09: AuthController, AuthServiceImpl, PhoneVerificationController/Service.
H07: HostDashboardController/Service.
H08: NoticeController/Service and HostNotificationsPage.
Java paths are under src/main/java/org/hlrcs/controller or service (AuthServiceImpl under service/impl).

The applicant USER flow that grants ROOM_HOST is outside this existing-host diagram. Property review is performed by eligible Staff, not the host.
Contract actions group preparation, optional scanning, owner signing and issuing a tenant link; tenant signing is performed separately by the tenant.
Billing actions include schedule configuration, drafts, issuance, payment recording and balance/history viewing. Payment recording is not a payment gateway.
Prototype support screens and capability-specific supporting-service management are excluded.
